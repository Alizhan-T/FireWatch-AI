# FireWatch: постоянный сервер и проверка подключения

## Развернуть сервер

Нужны Linux-сервер с Docker Compose, домен с DNS A/AAAA на этот сервер,
открытые входящие TCP 80/443 (UDP 443 необязателен) и доступ сервера к камерам.
Не создавайте AAAA-запись без рабочего IPv6. Исходящий HTTPS нужен для Firebase.

Из корня репозитория:

```bash
cp .env.production.example .env.production
mkdir -p secrets
chmod 700 secrets
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

В `.env.production` укажите свой `FIREWATCH_DOMAIN` (только имя хоста) и полученный
`API_ACCESS_TOKEN`. Храните токен в менеджере паролей. Файлы `.env.production`
и `secrets/` исключены из Git. Не отправляйте ключи в чат и не добавляйте их в коммиты.

```bash
chmod 600 .env.production
docker compose --env-file .env.production config --quiet
docker compose --env-file .env.production up -d --build
docker compose --env-file .env.production ps
docker compose --env-file .env.production logs --tail=100 backend caddy
```

Caddy запрашивает и обновляет TLS-сертификат домена. Порт API 8000 наружу не публикуется.
Сервер работает без root, с одним процессом Uvicorn. SQLite, камеры и доказательства
сохраняются в volume `firewatch_data`, сертификаты — в `caddy_data`.
Не запускайте несколько реплик backend: каждая создаст отдельный сканер.
Не применяйте `down -v`, если нужно сохранить данные. Логи ограничены по размеру;
доказательства автоматически не удаляются — контролируйте свободное место.

`restart: unless-stopped` восстанавливает упавший процесс после сбоя/перезапуска хоста.
Статус Docker `unhealthy` сам по себе **не** перезапускает зависший контейнер.
Для эксплуатации подключите внешний контроль `/ready` и уведомление оператору.

В iPhone: Настройки → адрес `https://ВАШ_ДОМЕН` → тот же API key → «Сохранить и проверить».
Проверьте вход по Wi-Fi и мобильной сети. Ошибку сертификата нельзя исправлять отключением TLS.

## Камеры и проверка готовности

Добавьте выданные оператором RTSP/HLS адреса и фактические координаты через приложение.
Пароль камеры остаётся в конфигурации сервера. Сервер должен иметь маршрут к камере;
приватный адрес из домашней сети не станет доступен VPS без настроенной сети/VPN.
«Проверить поток» должен вернуть свежий кадр; «Анализировать» — `real_model`.

В Compose автосканирование включено, но без камер готовность возвращает HTTP 503.
По умолчанию тревога требует 3 последовательных кадров одной угрозы с confidence ≥0.5.
Чистый кадр, низкая уверенность и ошибка потока сбрасывают подтверждение.
Огонь и огонь+дым подтверждают одну угрозу; один дым не подтверждает огонь.
Ручной анализ по кнопке остаётся анализом одного кадра.

`CAMERA_AUTO_SCAN_INTERVAL_SEC` — пауза **между полными обходами**, а не гарантированный
интервал каждой камеры. Задержка тревоги включает захват/анализ всех камер и подтверждение.
Порог и число кадров требуют подбора по вашим дневным/ночным записям, туману, бликам,
закатам и реальным случаям огня/дыма. Эта фильтрация не доказывает отсутствие ложных тревог.

| Адрес | Авторизация | Значение |
|---|---|---|
| `/live` | Не нужна | Процесс отвечает; не подтверждает работу камер |
| `/health` | `X-API-Key` | Модель, Firebase, база, счётчики |
| `/ready` | `X-API-Key` | 200 только при работающем сканере, модели, FFmpeg и свежих успешных анализах камер; иначе 503 |
| `/monitoring/status` | `X-API-Key` | Успешные/ошибочные проверки, ожидающие подтверждения, результаты по камерам |

`/ready` не требует Firebase: локальный мониторинг может работать без push. Firebase
проверяется отдельно. Счётчики действуют в пределах одного процесса и сбрасываются при перезапуске.

## Push на настоящий iPhone

1. Firebase iOS bundle ID: **kz.firewatch.native**. Поместите свой
   `GoogleService-Info.plist` в `FireWatchNative/FireWatchNative/`.
2. В Apple Developer включите Push Notifications у App ID. Загрузите APNs `.p8` ключ
   в Firebase Cloud Messaging; выберите свою команду подписания в Xcode.
3. Сохраните Firebase Admin JSON на сервере в `secrets/firebase-service-account.json`.
   Файл должен читаться UID 10001 внутри контейнера; каталог на хосте оставьте закрытым.
   Установите `FIREBASE_CREDENTIALS=/run/secrets/firebase-service-account.json`
   в `.env.production`, пересоздайте backend командой `up -d`.
4. Перегенерируйте Xcode-проект, запустите на iPhone, разрешите уведомления.
5. Нажмите «Отправить тестовое уведомление». Это нейтральное тестовое сообщение только
   на выбранный iPhone. `sent=1` означает принятие Firebase; подтвердите баннер на телефоне.
   Проверьте также при свёрнутом приложении и на заблокированном экране.

Для App Store/TestFlight provisioning должен использовать production APNs entitlement;
текущая конфигурация XcodeGen предназначена для development-запуска.

## Проверить модель и длительную работу

Из `backend/` в окружении с зависимостями:

```bash
python tools/evaluate_model.py --manifest tests/fixtures/evaluation.csv --repeats 25 --output reports/fixtures.json
```

Для своих кадров создайте CSV `path,label`: пути относительно CSV, метки `fire`, `smoke`,
`fire_smoke`, `none`. Команда считает TP/FP/FN/TN отдельно для огня/дыма и время inference.
Повторы измеряют нагрузку, а не увеличивают размер выборки. Два встроенных кадра —
только проверка работоспособности, не оценка качества в реальном лесу.

После успешных `/ready` и проверки камеры запустите наблюдение на отдельном хосте:

```bash
read -s -p 'API key: ' API_ACCESS_TOKEN
export API_ACCESS_TOKEN
python tools/soak_check.py --url https://ВАШ_ДОМЕН --duration 86400 --interval 60 --output reports/soak-24h.jsonl
```

Не закрывайте процесс; для VPS используйте tmux/systemd. Команда не меняет настройки
и не отправляет push. Она записывает HTTP-ошибки, неготовность, счётчики и замеченные
перезапуски; завершает работу ненулевым кодом при проблемах. Выберите новое имя отчёта
при повторном запуске. Промежутки между пробами не проверяются непрерывно.

Отдельно проверьте отключение/возврат камеры, перезапуск сервера, сохранение событий,
читаемость доказательств, повторные тревоги и рост использования CPU/RAM/диска при
вашем количестве камер. Не используйте учебные кадры как подтверждение полевой надёжности.

## Резервная копия

Для согласованной копии остановите backend, скопируйте весь volume `firewatch_data`
(база, файлы `-wal/-shm`, медиа, камеры), затем снова запустите backend. Проверьте
восстановление в отдельном окружении. Ключи Firebase и `.env.production` храните отдельно.

Источники по настройке: [Caddy HTTPS](https://caddyserver.com/docs/automatic-https),
[Firebase Admin send](https://firebase.google.com/docs/cloud-messaging/send/admin-sdk).
